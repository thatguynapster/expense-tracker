## Priority 1 — Cloud backup / sync (Finding §1.3)

**Why first:** a lost, reset, or uninstalled phone currently destroys all financial history with zero recovery path.

### Architecture decisions (2026-07-02)

- **Separate project, not part of this workspace.** Sync backend is built as its own Next.js app in a new top-level folder `folio-server/` (sibling to `artifacts/`, `docs/`, etc.), **not** added to `pnpm-workspace.yaml` and **gitignored** so it's never committed alongside this repo.
- **Database: MongoDB** (matches the original PRD, not the Postgres/Drizzle setup that was scaffolded in `artifacts/api-server`).
- **Access control: shared secret / API key.** No real login system — a static long-lived key sent in a request header, checked against a server-side env var. Appropriate for a genuinely single-user app; revisit if this ever needs multi-user or web access.
- **Hosting: Vercel.** Native fit for Next.js, minimal ops.
- **Sync unit: still no SQLite migration.** The mobile app's local storage stays on AsyncStorage in this pass — see the delta-sync redesign below for how the _sync mechanism_ changed; SQLite migration is still explicitly deferred (see §5.8), for the same reasons as originally noted: a real future improvement, but not required to solve the actual data-loss problem, and bundling it in now would double the risk of an already-large change.
- **Conflict handling: assume one active device at a time.** This is a single-user personal app; the working assumption is you're never running it on two phones with unsynced local changes simultaneously. Sync is effectively backup/restore (push on every change when online, pull on fresh install), not real multi-device merge. This assumption is unchanged by the delta-sync redesign below — a plain upsert-by-id still means "whoever pushes last wins," no per-record merge logic. If that assumption turns out wrong in practice, revisit with proper conflict resolution — flagged here so it's a conscious tradeoff, not an oversight.
- **`artifacts/api-server` is being removed** (Express/Postgres/Drizzle scaffold) — superseded by `folio-server`, keeping two half-built backends around would just cause confusion about which one is real.

### Redesign: delta sync + tombstones (2026-07-06)

The original design above (full-blob push/pull — delete everything server-side, then re-send the entire local dataset on every sync) was replaced before mobile-side wiring began, because it doesn't scale: every sync would ship the _entire_ transaction history, and every push would wipe + rewrite the server's whole dataset, regardless of how small the actual change was. The revised design:

- **Dirty-flag delta sync.** Every record (`Account`, `Category`, `Transaction`, `DisciplineState`, on both the mobile app and the Prisma schema) gained a `syncedAt: string | null` field — `null` means dirty (not yet synced), a timestamp means it was last confirmed synced at that time. Every mutation sets `syncedAt: null` on whatever record(s) it touches or creates. A sync push now collects only the currently-dirty records across all four collections and sends just those — not the full dataset. Server-side, `pushBlob` changed from delete-all-then-recreate to a per-record `upsert`-by-`id` (wrapped in one `$transaction` per push for atomicity). Sync cost is now proportional to what actually changed, not total history.
- **Tombstone deletes, on all four models.** Every model also gained `deletedAt: string | null`. Deleting a record (currently only `deleteCategory` — no delete feature exists yet for accounts/transactions/discipline state) doesn't remove it locally; it sets `deletedAt` + `syncedAt: null` (dirty) instead, so the tombstone itself gets synced. The server hard-deletes its copy on receiving a `deletedAt`-set record (via idempotent `deleteMany`, not `delete` — safe to retry if a push succeeds server-side but its response never reaches the client). Once the push confirms success, the mobile app purges the tombstoned record from local storage entirely — it doesn't just mark it synced, since a deleted-and-confirmed record no longer needs to exist anywhere. `deletedAt` was added to `Transaction` and `DisciplineState` too even though neither has a delete feature today (transactions are an immutable ledger per the PRD; discipline state is an internal singleton with no plausible delete path) — front-loaded per explicit direction, so a future delete feature on any model doesn't require another sync-layer change.
- **Delete confirmation prompts.** Any delete action must warn the user it's permanent and cannot be undone before proceeding. Applied now to the one delete feature that exists (`deleteCategory` in Settings — confirm-panel copy strengthened to state permanence explicitly); the same rule applies to any future account/transaction delete feature (see §5.4) when built.
- **Types still come from the Prisma schema on the server side** (unchanged rule) — `folio-server/lib/sync.ts`'s `SyncBlob` type remains composed entirely from Prisma-generated model types, now including their `deletedAt` fields. The mobile app's `lib/types.ts` interfaces are hand-maintained to mirror the Prisma schema field-for-field (Expo/React Native can't import the Prisma-generated client directly, being a separate runtime/project) — this mirroring is a manual-sync responsibility going forward, not automated.
- **Testing infrastructure added.** Neither project had a test runner before this work. Added Vitest to `folio-server` (task 1.2 onward) and, in this redesign, to `artifacts/expense-tracker` as well — scoped only to pure logic (`utils/*.test.ts`, `lib/*.test.ts`; store/UI code that depends on React Native/AsyncStorage/Expo Router is not covered, consistent with the existing untested state of `store/useStore.ts` before this change). Fixed a pre-existing bug in the root `pnpm-workspace.yaml` as a byproduct: it excluded `@rollup/rollup-win32-x64-msvc` (comment: "replit uses linux-x64 only"), which silently blocks any Vite/Vitest-based tooling on a native Windows dev machine (this one). Removed just that one exclusion; the rest of the platform-pruning list (which optimizes for Replit's Linux x64 deploy target) is untouched.

## Random Thoughts

**Resolved via §6.3 (2026-07-10).** The recommendation below — model this via the Loan/LoanPayment pattern rather than an income-split exemption flag — is what shipped, with zero new data model needed. Loans were relabeled to "IOUs" in the UI so the existing feature reads naturally for both a cash loan and a reimbursement/pass-through payment. See §6.3 for details.

That's a real gap, but I'd push back on solving it inside "income."

The core issue: this app's entire model is built around one hard rule — every income transaction enforces the 10% minimum savings split, and Safe-to-Spend/Discipline Debt are derived from that assumption holding for every income record. If you add an "exempt from split" toggle to income, you're not adding a flag, you're carving an exception into the one invariant everything else depends on — and now every future income-related calculation has to ask "was this a real income or a pass-through?"

The actual nature of the money matters here: holding money for colleagues isn't income at all — it was never yours, and it doesn't belong in your Safe-to-Spend math, your savings rate, or your Discipline Debt tracking. Structurally it's much closer to what you just built for loans: money that moves through an account without being your income or expense. In fact it's almost the mirror image of a loan — instead of you lending money out, someone is temporarily giving you money to hold or forward.

Given you already have the Loan/LoanPayment pattern (debits/credits an account directly, no Transaction created, doesn't touch Safe-to-Spend or Discipline Debt), I'd model this the same way rather than reworking income: something like a "Held Funds" or "Custody" record — who it's for, amount, whether it's been paid out — that credits/debits a spendable account without ever being classified as income. That keeps the income invariant intact and gives you a clean audit trail for the money you're holding, which plain income with a bypassed split wouldn't give you nearly as well.
